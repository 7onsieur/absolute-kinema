# animated-explainer v0.4-rc2 — Fresh-session test plan

For an independent tester, in a new environment, with no prior context from development. Expect
roughly 30–45 minutes including Kokoro's one-time model download. Report back: which steps passed,
which failed, and your own judgment on the final caption/voice quality (step 7 is the one no
automated check can do).

## 0. Prerequisites
- Ubuntu 24.04 x86_64 (other platforms are untested — note your platform if different).
- Python 3.13 and FFmpeg available.
- Network access to PyPI and to GitHub (`github.com`/`githubusercontent.com`) at least once, for
  the Kokoro model download. (Hugging Face access is NOT required for this release's default path.)

## 1. Unzip and install
```bash
unzip animated-explainer-v0.4-rc2.zip
cd animated-explainer
sudo apt-get update
sudo apt-get install -y ffmpeg fonts-inter fonts-dejavu espeak-ng
python3 -m pip install -r requirements.txt
```
**Pass/fail:** installation completes with no errors.

## 2. Run the automated test suite
```bash
python3 -m pytest -q tests/
```
**Expected:** all tests pass except one `skip` (a pre-existing, unrelated `NO_ESPEAK` marker — only
fires if espeak-ng truly isn't installed).

**About the Kokoro-specific tests:** they locate model weights the same way the skill itself does —
the `AE_KOKORO_MODEL_DIR` environment variable if you set it, otherwise the standard per-user cache
(`~/.cache/animated-explainer/kokoro`). If no model weights are found there yet, those specific
tests **skip** (reported as part of the one skip count only if nothing else is also skipped —
otherwise you'll see additional skips, which is correct and expected, not a failure) rather than
failing or faking results. To make them run for real on a first pass, either run step 4 once first
(which downloads the models to the default cache) and then re-run the suite, or point
`AE_KOKORO_MODEL_DIR` at a folder you've already populated:
```bash
AE_KOKORO_MODEL_DIR=/path/to/your/kokoro/models python3 -m pytest -q tests/
```
If any non-Kokoro test fails, or a Kokoro test fails (as opposed to skips) with models present,
stop and report the failure output — do not continue to manual testing yet.

## 3. List Kokoro voices
```bash
python3 scripts/make_video.py voices --engine kokoro
```
**Expected:** a list of ~11 voices, with `bf_emma` marked as the one reviewed and accepted for
this skill.

## 4. Create and validate a Kokoro-narrated project
```bash
python3 scripts/make_video.py new my_test
```
Edit `my_test/project.yaml`'s `narration:` block to:
```yaml
narration:
  audio: null
  script:
    - {id: s1, text: "This is a short test of the new Kokoro narration engine."}
  tts:
    enabled: true
    engine: kokoro
    voice: bf_emma
    speed: 1.0
scenes:
  - id: intro
    narration: [s1]
    elements:
      - {type: title, text: "Kokoro test", pos: center, enter: pop}
```
```bash
python3 scripts/make_video.py validate my_test/project.yaml
```
**Expected (first run):** a message that the Kokoro model files are downloading (a one-time, ~140MB
download from GitHub Releases), then a line starting `OK: ... timing`. Two outcomes are both
correct and expected, not a bug either way:
- `timing exact (from TTS engine's own duration output)` — every word got exact, model-native
  timing (the common case for a short, simple sentence like this one).
- `timing exact for N/M words (from TTS engine's own duration output); <k> word(s) partially
  estimated - see SKILL.md 'AI narration' (merged phoneme groups)`, plus a printed note — this
  means Kokoro's phonemizer ran a couple of adjacent words together with no gap (a documented,
  measured behavior, not a crash), and the skill localized a bounded estimate to just that
  pair/run rather than discarding the whole sentence's real timing. This is more likely on a
  longer or more naturally-phrased sentence than the one-liner above.

**If the model download fails**, you should see a specific error naming the GitHub Releases URLs
and a manual-download alternative — not a crash with no explanation, and not a fallback to any
paid service.

## 5. Preview, render, and check the output
```bash
python3 scripts/make_video.py preview my_test/project.yaml
python3 scripts/make_video.py render my_test/project.yaml
ffprobe -v error -show_entries stream=codec_type my_test/output/my_test.mp4
```
**Expected:** the render completes; `ffprobe` shows both a `video` and an `audio` stream; an
`my_test.UNVERIFIED.srt` file and `my_test.qa_report.md` exist; the QA report lists no issues and
`has_audio: True`.

**Audio lead-in check (fixed in rc2):** the ~0.6s of silence before the voice starts must be real,
decodable silence, not just a container-level timestamp a strict decoder could skip past. Verify by
decoding to raw PCM directly (which ignores all container timestamps) and confirming the first
~0.5s is near-silent:
```bash
ffmpeg -v error -i my_test/output/my_test.mp4 -vn -ac 1 -ar 16000 -f s16le -t 0.5 - | \
  python3 -c "import sys,struct; d=sys.stdin.buffer.read(); s=struct.unpack(f'<{len(d)//2}h', d); print('RMS:', (sum(x*x for x in s)/len(s))**0.5)"
```
**Expected:** a low RMS value (well under a few hundred, out of a possible ±32768) — i.e. genuine
near-silence in the decoded samples themselves, not just in the container's displayed timing.

## 6. Run caption verification
```bash
python3 scripts/make_video.py verify-captions my_test/project.yaml
```
Read `my_test/output/my_test.captions_review.md`.
**Expected:** 0 (or a small, explainable number of) possible-missing-word spots.

## 7. The one check only a human can do
**Watch `my_test/output/my_test.mp4` with sound, reading every caption as it appears.** Judge:
- Does the voice sound natural and clearly British (not robotic)?
- Do the captions appear and disappear in sync with what is actually being said — no visible lag
  building up toward the end?
- Does the picture appear to start right away (not visibly delayed), with the voice beginning
  audibly, cleanly, and on time after the short lead-in — not abruptly, and not noticeably late?

If all of this is true, approve it yourself:
```bash
python3 scripts/make_video.py approve-captions my_test/project.yaml --name "Your Name"
```
**Do not approve if you aren't satisfied** — that is the entire point of this checkpoint.

## 8. Confirm the other paths still work (regression spot-check)
```bash
python3 scripts/make_video.py validate examples/water_cycle/project.yaml   # silent/no-audio path
python3 scripts/make_video.py voices --engine espeak                        # espeak path
```
**Expected:** both succeed, unaffected by the Kokoro changes. Separately, try a short project with
a real user-recorded `narration.audio` file (any FFmpeg-readable format) and no `tts:` block, and
confirm forced alignment and caption export still work as in earlier releases.

## 9. Render-cache invalidation sanity check (optional, for a technical reviewer)
Render `my_test` once, note the segment video files' timestamps under
`my_test/work/my_test/segments_full/`, change the narration script text slightly, re-render, and
confirm the log reports clearing previously-cached segments and the segment files' timestamps
change. This confirms a changed narration can't silently reuse a stale video segment.

## Report back
For each step: pass, fail, or "didn't get to it," plus:
- Your own judgment on voice quality, caption sync, and the audio lead-in (step 7) — this is the
  one thing this report cannot certify for you.
- Which `validate` outcome you saw in step 4 (fully exact, or partially estimated) — both are
  correct, but it's useful to know which sentences trigger which.
- Anything in `V0.4_RELEASE_REPORT.md`/`V0.4_RC2_RELEASE_REPORT.md`'s "explicitly NOT verified"
